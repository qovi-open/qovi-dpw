Qovi DpW — le trousseau ouvert par Qovi

Votre trousseau de mots de passe intuitif, ouvert par Qovi sans mot de passe maître, synchronisé sans cloud par QR entre PC et mobile. Windows Linux Android macOS · iOS : depuis les sources

Ce qu'il vous faut

  • L'app Qovi sur votre téléphone, avec votre compte Qovi.
  • Qovi DpW sur chaque appareil où vous voulez vos mots de passe : PC Windows (installeur .msi), PC Linux (paquet .deb) et téléphone Android (.apk).
  • Mac et iPhone : pas encore d'installeur. Un développeur peut fabriquer DpW lui-même depuis les sources (onglet Développeur, « Construire »).

Installer

🪟 Windows

Ouvrez qovi-dpw.msi. Windows peut afficher « éditeur inconnu » : choisissez Informations complémentaires, puis Exécuter quand même. DpW s'installe dans Program Files, avec un raccourci dans le menu Démarrer et sur le bureau.

🐧 Linux

Pour Debian, Ubuntu et leurs dérivées, en 64 bits (amd64). Dans un terminal, depuis le dossier où vous avez téléchargé le paquet :

sudo apt install ./qovi-dpw.deb

apt installe aussi ce qui manque (bibliothèque GTK 3). DpW s'installe dans /opt/qovi-dpw, avec une entrée Qovi DpW dans le menu des applications ; on peut aussi le lancer par la commande qovi-dpw. Pour le retirer : sudo apt remove qovi-dpw (votre trousseau, rangé dans votre dossier personnel, n'est pas effacé).

🤖 Android

Ouvrez qovi-dpw.apk et autorisez l'installation depuis cette source si le téléphone le demande.

L'APK est signée par « Qovi DpW » (empreinte SHA-256 du certificat : 69:F1:46:20:5E:D6:40:C6:65:73:B4:E4:A9:5D:5C:4E:69:27:23:EB:DA:C7:5D:9A:DE:BC:26:C1:30:07:9E:D6). Une APK signée autrement n'est pas la nôtre.

Une nouvelle version s'installe par-dessus l'ancienne : vos mots de passe sont gardés.

Ouvrir le trousseau

1
Saisissez votre adresse e-mail Qovi. Elle est retenue pour la prochaine fois ; le ✕ à côté l'oublie.
2
Touchez le grand bouton d'entrée.
3
Validez la demande dans l'app Qovi sur votre téléphone. Si DpW est sur le même téléphone, Qovi s'ouvre tout seul, puis vous ramène dans DpW après la validation.
Aucun mot de passe maître à retenir : c'est votre validation Qovi qui ouvre le trousseau. La toute première ouverture sur un appareil peut prendre jusqu'à une minute.

Utiliser

  • Rechercher : tapez un ou plusieurs mots. « banque ch » trouve les entrées qui contiennent les deux mots, dans le nom ou dans la note, sans tenir compte des majuscules ni des accents. Le ✕ efface la recherche.
  • Sur chaque ligne, quatre gros boutons : ✏ ouvrir la fiche ; 👤 copier l'identifiant ; 🔑 copier le mot de passe (effacé du presse-papiers après 30 secondes) ; ↗ ouvrir le site, si l'entrée a une adresse web.
  • + crée une entrée, avec un mot de passe fort déjà proposé.
  • Dans la fiche : 🗑 supprime, ✓ enregistre, ← revient sans enregistrer.

Synchroniser vos appareils, sans cloud

1
Sur les deux appareils, ouvrez DpW avec le même compte.
2
Touchez ⟳ sur les deux.
3
Sur l'un, touchez Envoyer : un QR s'affiche. Sur un ordinateur (Windows ou Linux), c'est le seul bouton : c'est le téléphone qui scanne.
4
Sur le téléphone, touchez Recevoir et scannez le QR.

Les deux appareils finissent avec le même trousseau. Si une entrée a été modifiée des deux côtés, les deux versions sont gardées : l'une porte la mention « copie du … », à vous de choisir. Une suppression se propage aux autres appareils.

Réglages

Touchez Qovi DpW en haut de l'écran :

  • Langue : FR, DE, IT ou EN.
  • Verrouillage après inactivité : 5 min, 15 min, 30 min, 1 h ou 2 h.
  • Ancien trousseau DpW (fichier _DpW.aes) : Choisir le fichier, puis Importer avec son ancienne clé. Le fichier d'origine n'est pas modifié.

Sécurité

  • Le trousseau est stocké uniquement sur vos appareils, chiffré. Rien n'est gardé dans un cloud.
  • Il se verrouille seul après une période sans activité (60 minutes par défaut) et DpW revient à l'écran d'ouverture.
  • Le bouton de sortie, en haut à gauche, verrouille tout de suite.

L'idée

DpW montre comment une application sans serveur à elle et sans clé privée de site peut s'appuyer sur Qovi pour ouvrir un coffre local. Le client (Flutter : Windows, Linux, Android, macOS et iOS, même code) est fourni en sources ; le service DpW côté serveur fait partie de la plateforme Qovi.

1. Ouvrir sans clé privée : le parcours « Alone »

Une app de bureau ou mobile ne peut pas garder de clé privée de site : elle serait lisible par quiconque possède l'app. DpW n'embarque donc que des valeurs publiques : la clé Alone du kit et la clé publique du site DpW.

1. CH1 GET <api>/RST/SiT_1_Edr?P=… ─▶ Qovi demande d'ouverture (clé Alone + clé publique du site) 2. CH4 TLS <api>:6404 ─▶ Qovi attente du GO (130 s), en G1 : kid (empreinte) + G1(i:1), puis G1(i:2) ◀─ Qovi l'usager valide sur son mobile 3. CH5 TLS <dpw>:6999 ─▶ DpW remise de la clé du trousseau SoK.U, chiffrée avec Ch5.U issue de la validation

Sur CH4, la clé de transaction Prv_NaP ne circule jamais : la 1re trame porte son empreinte kid = 16 premiers octets de HMAC-SHA256(Prv_NaP, "qovi-ch4-kid"), puis les messages en G1 avec la clé HMAC-SHA256(Prv_NaP, "qovi-ch4-gcm"). Si le canal est coupé pendant l'attente (par exemple quand l'usager passe dans l'app Qovi du même téléphone), DpW se reconnecte et renvoie i:1 seul : le serveur renvoie alors le GO déjà donné, sans relancer le vote.

La clé du trousseau est gardée par le service DpW, par compte (table dpw_keys). Tous les appareils d'un même compte reçoivent la même clé : c'est ce qui permet la synchro. Elle n'est jamais écrite sur disque côté client ; elle disparaît au verrouillage.

2. Le coffre local

  • Fichier dans le stockage privé de l'app, invisible pour l'usager.
  • Format : "DPW2" + nonce (12) + AES-256-GCM(JSON) + tag (16), clé = HMAC-SHA256(SoK.U, "qovi-dpw-vault-v2"), "DPW2" en données associées. Un fichier modifié ou une mauvaise clé est refusé.
  • Écriture atomique (fichier temporaire puis renommage) et 3 sauvegardes tournantes. Un fichier illisible n'est jamais écrasé.
  • Contenu : {"v":3,"cod":[entrées],"del":[traces de suppression]}.

3. La synchro par QR, sans cloud

L'appareil A affiche le QR, l'appareil S le scanne. A tire une clé de session en deux moitiés, MSB et LSB (2 × 128 bits).

Étape 4 A ─▶ DpW LSB + trousseau de A (chiffré avec la clé de session) QR A ─▶ S "DPWS" + MSB + code de transfert (MSB ne passe JAMAIS par le serveur) Étape 5 S ─▶ DpW code ; reçoit LSB + trousseau de A, fusionne, dépose son trousseau Étape 3 A ─▶ DpW récupère le trousseau de S et fusionne
Le service ne détient jamais la clé de session complète : il relaie des blocs qu'il ne peut pas lire. Les blocs sont en AES-256-GCM. Le service vérifie que A et S sont ouverts sur le même compte, et le QR est à usage unique.

Fusion (règle B), symétrique

merge(a, b) = merge(b, a) : les deux appareils finissent identiques.

  • Une entrée modifiée d'un seul côté : le changement est pris.
  • Modifiée des deux côtés : les deux sont gardées, la plus ancienne en « copie du … ».
  • Une suppression se propage, sauf si l'entrée a été modifiée après. Les traces de suppression sont gardées 1 an.

Il faut un Mac avec Xcode et Flutter. Les commandes se passent dans le dossier dpw/qfa_dpw des sources.

Identifiant et nom à changer. Les sources portent les identifiants de Qovi : ch.qovi.dpwx (macOS, dans macos/Runner/Configs/AppInfo.xcconfig) et ch.qovi.dpwi (iOS, avec l'équipe Apple 583T5KBF35, dans ios/Runner.xcodeproj). Remplacez-les par les vôtres, par exemple com.exemple.dpw. Si vous redistribuez votre version, elle ne doit pas s'appeler « Qovi » ni porter les logos Qovi (voir NOTICE).
# macOS : l'app (.app) se trouve ensuite dans build/macos/Build/Products/Release/
flutter build macos --release
# iOS : iPhone branché au Mac, équipe et identifiant choisis dans Xcode
open ios/Runner.xcworkspace
flutter run --release

  • iOS : dans Xcode, onglet Signing & Capabilities de la cible Runner, choisissez votre équipe et votre identifiant. Sur l'iPhone, activez Réglages › Confidentialité et sécurité › Mode développeur.
  • Compte Apple gratuit : l'app installée expire au bout de 7 jours (il suffit de la réinstaller), et la capacité Associated Domains n'est pas disponible : retirez-la dans Signing & Capabilities, sinon la signature échoue. Sans elle, pas de retour automatique depuis Qovi (section 5) : revenez dans l'app à la main après avoir validé, l'ouverture se termine.
  • Retour automatique depuis Qovi : les domaines dpw.qovi.ch et tst.dpw.qovi.ch ne reconnaissent que l'app publiée par Qovi. Pour votre propre version, utilisez votre domaine en suivant la section 5.

5. Se connecter avec Qovi depuis une app mobile : le retour automatique

Quand votre app et l'app Qovi sont sur le même téléphone, votre app peut envoyer l'usager dans Qovi pour valider, et Qovi le ramène tout seul dans votre app après le vote. DpW le fait sur Android et sur iPhone ; cette section explique comment le faire pour votre app. Sans retour automatique, tout fonctionne quand même : l'usager revient à la main dans votre app, qui termine la connexion.

Le parcours

1. CH1 votre app ─▶ Qovi demande, avec la clé Alone ; g.u = identifiant de la demande 2. CH4 votre app ─▶ Qovi G1(i:1) puis G1(i:2) : demande de vote 3. votre app ouvre https://qovi.ch/app/auth?act=<g.u> ─▶ le système passe la main à l'app Qovi (ou à une page qui invite à l'installer) 4. l'usager valide dans Qovi 5. Qovi ouvre <adresse de retour du site>?act=<g.u>&v=ok|ko (~1,5 s après Oui → v=ok, ou Non → v=ko ; tout de suite avec v=ko si l'usager abandonne) ─▶ Android / iOS rouvre votre app (lien vérifié) 6. CH4 votre app revient au premier plan : elle ferme CH4 et se reconnecte par G1(i:1) SEUL ─▶ Qovi lui redonne le GO déjà donné
  • Seul le GO reçu par CH4 fait foi. act et v ne servent qu'à l'affichage ; votre app peut les ignorer (DpW ne les lit pas).
  • Ouvrez le lien d'aller après l'envoi de i:2, pas avant : sinon le système peut endormir votre app avant la demande de vote, et Qovi s'ouvre sans rien à valider.
  • Pendant que Qovi est au premier plan, le système endort votre app et la connexion CH4 peut mourir sans bruit. Au retour, fermez CH4 vous-même : la reconnexion par i:1 seul récupère le GO. N'envoyez jamais i:2 à la reconnexion, il relancerait le vote.
  • Dans DpW : qoviAuthUri, _toQovi et _waitGo dans lib/core/alone.dart (ouverture par url_launcher en LaunchMode.externalApplication, fermeture de CH4 par AppLifecycleListener.onResume).

Pourquoi c'est sûr

  • L'adresse de retour ne vient jamais de votre app. Le lien d'aller ne porte que g.u (un identifiant de demande, pas un secret). Le serveur Qovi lit l'adresse dans la fiche du site propriétaire de la clé Alone, la vérifie, puis la joint à la demande envoyée au mobile. Une app malveillante ne peut donc pas faire ouvrir l'adresse de son choix.
  • Contrôles du serveur : https, ni port ni identifiants dans l'adresse, 300 caractères au plus, et hôte = le domaine du site ou un de ses sous-domaines. Sinon le retour n'a pas lieu (l'usager revient à la main).
  • Le bon téléphone, le bon moment : Qovi n'ouvre le retour que si un lien d'aller (https://qovi.ch/app/auth?act=…) a été reçu par Qovi sur ce téléphone depuis moins de 3 minutes, et chaque lien d'aller ne sert qu'à un retour. Une validation lancée depuis un autre appareil (par exemple DpW sur un PC) n'a pas de lien d'aller sur le téléphone : elle ne fait pas surgir votre app.
  • La bonne app : Android et iOS ne rouvrent votre app que si votre domaine la déclare (fichiers assetlinks.json et apple-app-site-association ci-dessous). Une autre app ne peut pas se faire ouvrir à sa place.

Trois choses à mettre en place

Dans les exemples, remplacez votre-domaine.ch par le domaine de votre site dans Qovi, com.exemple.app par l'identifiant de votre app et ABCDE12345 par votre équipe Apple.

A. Dans votre app

Android, dans android/app/src/main/AndroidManifest.xml (celui de DpW est un exemple complet) :

<!-- singleTask : c'est l'instance qui attend le GO qui revient au premier plan -->
<activity android:name=".MainActivity" android:exported="true"
    android:launchMode="singleTask" android:taskAffinity="" …>
  <!-- le lien de retour ne doit pas devenir une route Flutter -->
  <meta-data android:name="flutter_deeplinking_enabled" android:value="false"/>
  <!-- retour de Qovi : lien vérifié (App Link) -->
  <intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <category android:name="android.intent.category.BROWSABLE"/>
    <data android:scheme="https"/>
    <data android:host="votre-domaine.ch"/>
    <data android:pathPrefix="/qovi-retour"/>
  </intent-filter>
</activity>
<!-- Android 11 et plus : permettre à l'app d'ouvrir le lien https vers Qovi -->
<queries>
  <intent><action android:name="android.intent.action.VIEW"/><data android:scheme="https"/></intent>
</queries>

iOS, dans ios/Runner/Runner.entitlements (capacité Associated Domains, compte Apple payant) :

<key>com.apple.developer.associated-domains</key>
<array>
  <string>applinks:votre-domaine.ch</string>
</array>

Pour les essais avec une app signée en développement, applinks:votre-domaine.ch?mode=developer fait lire le fichier directement sur votre site au lieu du cache d'Apple (réglage Mode développeur de l'iPhone requis). Retirez ?mode=developer pour TestFlight et l'App Store.

B. Sur le domaine de votre site

Trois adresses, servies en https, réponse 200, sans redirection. Les deux fichiers sont en application/json. Le chemin /qovi-retour est celui de DpW ; un autre convient, pourvu que l'app, les fichiers et la fiche du site disent le même.

https://votre-domaine.ch/.well-known/assetlinks.json (Android) : le paquet et l'empreinte SHA-256 du certificat qui signe votre APK (apksigner verify --print-certs votre.apk ; avec la signature par Google Play, prenez l'empreinte affichée dans la Play Console).

[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.exemple.app",
      "sha256_cert_fingerprints": ["AA:BB:…:FF"]
    }
  }
]

https://votre-domaine.ch/.well-known/apple-app-site-association (iOS) : fichier sans extension, équipe Apple + identifiant de l'app.

{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.exemple.app"],
        "components": [ { "/": "/qovi-retour" }, { "/": "/qovi-retour/*" } ]
      }
    ]
  }
}

Avec Apache, un .htaccess dans .well-known/ donne le bon type au fichier sans extension :

<Files "apple-app-site-association">
    ForceType application/json
</Files>

https://votre-domaine.ch/qovi-retour/ : une page de secours, affichée seulement si votre app n'est pas installée ou si le lien n'est pas (encore) vérifié. Elle invite à revenir dans l'app ou à l'installer. Elle ne doit ni lire ni afficher act et v (rien à en faire, et pas de risque d'injection), et répondre avec Cache-Control: no-store et <meta name="robots" content="noindex">. La page de dpw.qovi.ch en est un exemple.

C. Dans la fiche de votre site sur Qovi

1
Sur qovi.ch, ouvrez la page Administration du site en vous connectant avec le compte ch.qovi@votre-domaine.ch (celui qui a reçu la clé de votre site).
2
Dans la carte Retour vers votre app mobile, saisissez l'Adresse de retour (facultatif) : https://votre-domaine.ch/qovi-retour.
3
Touchez Enregistrer. Une adresse qui ne respecte pas les contrôles ci-dessus est refusée, avec la raison en clair.
  • Une seule adresse par site. Retirer (ou vider le champ puis Enregistrer) la supprime, après confirmation : plus de retour automatique.
  • La page exige une connexion de moins de 5 minutes ; chaque changement est tracé et signalé par e-mail à l'administrateur du site.
  • Le retour ne concerne que les demandes faites avec la clé Alone (apps sans clé privée, comme DpW). Un site web n'en a pas besoin : son retour se fait dans le même onglet du navigateur.

Vérifier et dépanner

# les deux fichiers : HTTP 200, content-type application/json, aucune ligne location:
curl -sS -D - -o /dev/null https://votre-domaine.ch/.well-known/assetlinks.json
curl -sS -D - -o /dev/null https://votre-domaine.ch/.well-known/apple-app-site-association
# Android : le domaine doit apparaître « verified »
adb shell pm get-app-links com.exemple.app
# sinon, redemander la vérification (le fichier doit être en ligne)
adb shell pm verify-app-links --re-verify com.exemple.app
# ouvrir le retour à la main : votre app doit passer au premier plan
adb shell am start -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "https://votre-domaine.ch/qovi-retour?x=1"
  • Android vérifie le lien à l'installation. Mettez assetlinks.json en ligne avant de diffuser l'app. Un téléphone dont la vérification a échoué ne verra pas le retour avant une mise à jour de l'app (ou --re-verify).
  • L'app s'ouvre en double, ou attend sans fin : vérifiez singleTask et taskAffinity="".
  • L'app s'ouvre sur un écran inattendu au retour : vérifiez flutter_deeplinking_enabled=false.
  • iPhone : Safari s'ouvre au lieu de l'app. iOS garde le fichier Apple en cache : après un changement, réinstallez l'app (ou utilisez ?mode=developer pendant les essais).
  • Rien ne se passe après le vote : la fiche du site n'a pas d'adresse de retour ; l'adresse est refusée par les contrôles (domaine, https, port) ; le lien d'aller a été reçu il y a plus de 3 minutes ; le lien d'aller s'est ouvert dans le navigateur au lieu de Qovi (Qovi absent, ou lien de qovi.ch pas encore vérifié sur ce téléphone : la page de secours de qovi.ch s'affiche) ; ou la version de Qovi est trop ancienne (Qovi des stores 1.0.13 ou plus conseillé). L'usager peut toujours revenir à la main.

Sécurité

  • Aucune clé privée dans l'app : seulement la clé Alone et la clé publique du site.
  • Clé du trousseau en mémoire seulement, effacée au verrouillage (60 min d'inactivité par défaut, réglable) avec le presse-papiers.
  • Mot de passe copié : effacé du presse-papiers après 30 s, et à la fermeture.
  • Canaux chiffrés et authentifiés : CH4, CH5 et la synchro utilisent l'enveloppe G1 = "G1" + base64(nonce 12 + AES-256-GCM + tag 16), avec une clé dérivée par usage (HMAC-SHA256) et le sens du message en données associées. Un message modifié, rejoué dans l'autre sens ou destiné à une autre transaction est refusé. Le tout passe en plus dans TLS.
  • Retour automatique : l'adresse vient de la fiche du site, jamais de l'app ; seul le GO de CH4 fait foi (section 5).
  • Import d'un ancien trousseau WL : texte base64 de IV + AES-256-CBC(contrôle sur 8 octets + JSON), clair en Windows-1252 ou UTF-8.

Qovi DpW — the keychain opened by Qovi

Your easy password keychain, opened by Qovi with no master password, synchronised without any cloud by QR code between PC and phone. Windows Linux Android macOS · iOS: from source

What you need

  • The Qovi app on your phone, with your Qovi account.
  • Qovi DpW on every device where you want your passwords: Windows PC (.msi installer), Linux PC (.deb package) and Android phone (.apk).
  • Mac and iPhone: no installer yet. A developer can build DpW from source (Developer tab, “Build”).

Install

🪟 Windows

Open qovi-dpw.msi. Windows may show “unknown publisher”: choose More info, then Run anyway. DpW installs into Program Files, with a shortcut in the Start menu and on the desktop.

🐧 Linux

For Debian, Ubuntu and their derivatives, 64-bit (amd64). In a terminal, from the folder where you downloaded the package:

sudo apt install ./qovi-dpw.deb

apt also installs what is missing (GTK 3 library). DpW installs into /opt/qovi-dpw, with a Qovi DpW entry in the applications menu; you can also start it with the qovi-dpw command. To remove it: sudo apt remove qovi-dpw (your keychain, kept in your home folder, is not deleted).

🤖 Android

Open qovi-dpw.apk and allow installation from this source if the phone asks.

The APK is signed by “Qovi DpW” (SHA-256 certificate fingerprint: 69:F1:46:20:5E:D6:40:C6:65:73:B4:E4:A9:5D:5C:4E:69:27:23:EB:DA:C7:5D:9A:DE:BC:26:C1:30:07:9E:D6). An APK signed otherwise is not ours.

A new version installs over the old one: your passwords are kept.

Open the keychain

1
Enter your Qovi e-mail address. It is remembered for next time; the ✕ next to it forgets it.
2
Tap the big entry button.
3
Approve the request in the Qovi app on your phone. If DpW is on the same phone, Qovi opens by itself, then brings you back to DpW after the approval.
No master password to remember: your Qovi approval opens the keychain. The very first opening on a device can take up to a minute.

Use

  • Search: type one or more words. “bank ch” finds the entries that contain both words, in the name or in the note, ignoring case and accents. The ✕ clears the search.
  • On each line, four big buttons: ✏ open the entry; 👤 copy the user name; 🔑 copy the password (cleared from the clipboard after 30 seconds); ↗ open the website, if the entry has a web address.
  • + creates an entry, with a strong password already suggested.
  • In the entry: 🗑 deletes, ✓ saves, ← goes back without saving.

Synchronise your devices, without any cloud

1
On both devices, open DpW with the same account.
2
Tap ⟳ on both.
3
On one of them, tap Send: a QR code is shown. On a computer (Windows or Linux) it is the only button: the phone does the scanning.
4
On the phone, tap Receive and scan the QR code.

Both devices end up with the same keychain. If an entry was changed on both sides, both versions are kept: one is marked “copy of …”, and you choose. A deletion spreads to the other devices.

The idea

DpW shows how an application with no server of its own and no private site key can rely on Qovi to open a local vault. The client (Flutter: Windows, Linux, Android, macOS and iOS, same code) is provided as source code; the DpW service on the server side is part of the Qovi platform.

1. Opening without a private key: the “Alone” flow

A desktop or mobile app cannot keep a private site key: anyone who has the app could read it. DpW therefore only embeds public values: the kit's Alone key and the public key of the DpW site.

1. CH1 GET <api>/RST/SiT_1_Edr?P=… ─▶ Qovi opening request (Alone key + public site key) 2. CH4 TLS <api>:6404 ─▶ Qovi wait for the GO (130 s), in G1: kid (fingerprint) + G1(i:1), then G1(i:2) ◀─ Qovi the user approves on their phone 3. CH5 TLS <dpw>:6999 ─▶ DpW delivery of the keychain key SoK.U, encrypted with Ch5.U from the approval

On CH4, the transaction key Prv_NaP never travels: the first frame carries its fingerprint kid = first 16 bytes of HMAC-SHA256(Prv_NaP, "qovi-ch4-kid"), then the messages in G1 with the key HMAC-SHA256(Prv_NaP, "qovi-ch4-gcm"). If the channel drops while waiting (for example when the user switches to the Qovi app on the same phone), DpW reconnects and sends i:1 only: the server then sends the GO already given, without starting the vote again.

The keychain key is kept by the DpW service, per account (dpw_keys table). All the devices of one account receive the same key: that is what makes synchronisation possible. It is never written to disk on the client; it disappears when the keychain locks.

2. The local vault

  • File in the app's private storage, invisible to the user.
  • Format: "DPW2" + nonce (12) + AES-256-GCM(JSON) + tag (16), key = HMAC-SHA256(SoK.U, "qovi-dpw-vault-v2"), "DPW2" as associated data. A modified file or a wrong key is rejected.
  • Atomic write (temporary file, then rename) and 3 rotating backups. An unreadable file is never overwritten.
  • Content: {"v":3,"cod":[entries],"del":[deletion marks]}.

3. QR synchronisation, without any cloud

Device A shows the QR code, device S scans it. A draws a session key in two halves, MSB and LSB (2 × 128 bits).

Step 4 A ─▶ DpW LSB + A's keychain (encrypted with the session key) QR A ─▶ S "DPWS" + MSB + transfer code (MSB NEVER goes through the server) Step 5 S ─▶ DpW code; receives LSB + A's keychain, merges, uploads its own keychain Step 3 A ─▶ DpW fetches S's keychain and merges
The service never holds the full session key: it relays blocks it cannot read. The blocks are AES-256-GCM. The service checks that A and S are open on the same account, and the QR code can be used only once.

Merge (rule B), symmetric

merge(a, b) = merge(b, a): both devices end up identical.

  • An entry changed on one side only: the change is taken.
  • Changed on both sides: both are kept, the older one as “copy of …”.
  • A deletion spreads, unless the entry was changed afterwards. Deletion marks are kept for 1 year.

5. Signing in with Qovi from a mobile app: the automatic return

When your app and the Qovi app are on the same phone, your app can send the user to Qovi to approve, and Qovi brings them back to your app by itself after the vote. DpW does this on Android and iPhone; this section explains how to do it for your app. Without the automatic return everything still works: the user goes back to your app by hand, and it completes the sign-in.

The flow

1. CH1 your app ─▶ Qovi request, with the Alone key; g.u = request identifier 2. CH4 your app ─▶ Qovi G1(i:1) then G1(i:2): vote request 3. your app opens https://qovi.ch/app/auth?act=<g.u> ─▶ the system hands over to the Qovi app (or to a page that invites the user to install it) 4. the user approves in Qovi 5. Qovi opens <site's return address>?act=<g.u>&v=ok|ko (~1.5 s after Yes → v=ok, or No → v=ko; at once with v=ko if the user gives up) ─▶ Android / iOS reopens your app (verified link) 6. CH4 your app comes back to the foreground: it closes CH4 and reconnects with G1(i:1) ONLY ─▶ Qovi gives it the GO already given
  • Only the GO received on CH4 counts. act and v are for display only; your app can ignore them (DpW does not read them).
  • Open the outbound link after sending i:2, not before: otherwise the system may put your app to sleep before the vote request, and Qovi opens with nothing to approve.
  • While Qovi is in the foreground, the system puts your app to sleep and the CH4 connection can die silently. When you come back, close CH4 yourself: reconnecting with i:1 only fetches the GO. Never send i:2 on reconnection: it would start the vote again.
  • In DpW: qoviAuthUri, _toQovi and _waitGo in lib/core/alone.dart (opened with url_launcher in LaunchMode.externalApplication, CH4 closed in AppLifecycleListener.onResume).

Why it is safe

  • The return address never comes from your app. The outbound link only carries g.u (a request identifier, not a secret). The Qovi server reads the address from the site record that owns the Alone key, checks it, then attaches it to the request sent to the phone. A malicious app therefore cannot have the address of its choice opened.
  • Server checks: https, no port and no credentials in the address, 300 characters at most, and host = the site's domain or one of its subdomains. Otherwise there is no return (the user goes back by hand).
  • The right phone, the right moment: Qovi only opens the return if an outbound link (https://qovi.ch/app/auth?act=…) was received by Qovi on this phone less than 3 minutes ago, and each outbound link serves for one return only. An approval started from another device (for example DpW on a PC) has no outbound link on the phone: it does not pop your app up.
  • The right app: Android and iOS only reopen your app if your domain declares it (assetlinks.json and apple-app-site-association files below). Another app cannot be opened in its place.

Three things to set up

In the examples, replace your-domain.com with your site's domain in Qovi, com.example.app with your app's identifier and ABCDE12345 with your Apple team.

A. In your app

Android, in android/app/src/main/AndroidManifest.xml (DpW's one is a complete example):

<!-- singleTask: the instance waiting for the GO is the one brought back -->
<activity android:name=".MainActivity" android:exported="true"
    android:launchMode="singleTask" android:taskAffinity="" …>
  <!-- the return link must not become a Flutter route -->
  <meta-data android:name="flutter_deeplinking_enabled" android:value="false"/>
  <!-- return from Qovi: verified link (App Link) -->
  <intent-filter android:autoVerify="true">
    <action android:name="android.intent.action.VIEW"/>
    <category android:name="android.intent.category.DEFAULT"/>
    <category android:name="android.intent.category.BROWSABLE"/>
    <data android:scheme="https"/>
    <data android:host="your-domain.com"/>
    <data android:pathPrefix="/qovi-retour"/>
  </intent-filter>
</activity>
<!-- Android 11 and later: allow the app to open the https link to Qovi -->
<queries>
  <intent><action android:name="android.intent.action.VIEW"/><data android:scheme="https"/></intent>
</queries>

iOS, in ios/Runner/Runner.entitlements (Associated Domains capability, paid Apple account):

<key>com.apple.developer.associated-domains</key>
<array>
  <string>applinks:your-domain.com</string>
</array>

For tests with an app signed for development, applinks:your-domain.com?mode=developer makes iOS read the file directly from your site instead of Apple's cache (the iPhone's Developer Mode setting is required). Remove ?mode=developer for TestFlight and the App Store.

B. On your site's domain

Three addresses, served over https, response 200, no redirect. Both files are application/json. The path /qovi-retour (“Qovi return”) is the one used by DpW; any path works as long as the app, the files and the site record agree.

https://your-domain.com/.well-known/assetlinks.json (Android): the package and the SHA-256 fingerprint of the certificate that signs your APK (apksigner verify --print-certs your.apk; with Google Play app signing, use the fingerprint shown in the Play Console).

[
  {
    "relation": ["delegate_permission/common.handle_all_urls"],
    "target": {
      "namespace": "android_app",
      "package_name": "com.example.app",
      "sha256_cert_fingerprints": ["AA:BB:…:FF"]
    }
  }
]

https://your-domain.com/.well-known/apple-app-site-association (iOS): file without extension, Apple team + app identifier.

{
  "applinks": {
    "details": [
      {
        "appIDs": ["ABCDE12345.com.example.app"],
        "components": [ { "/": "/qovi-retour" }, { "/": "/qovi-retour/*" } ]
      }
    ]
  }
}

With Apache, a .htaccess in .well-known/ gives the file without extension the right type:

<Files "apple-app-site-association">
    ForceType application/json
</Files>

https://your-domain.com/qovi-retour/: a fallback page, shown only if your app is not installed or the link is not (yet) verified. It invites the user to go back to the app or to install it. It must neither read nor display act and v (nothing to do with them, and no injection risk), and answer with Cache-Control: no-store and <meta name="robots" content="noindex">. The page on dpw.qovi.ch is an example.

C. In your site's record on Qovi

1
On qovi.ch, open the Site administration page by signing in with the ch.qovi@your-domain.com account (the one that received your site's key).
2
In the Return to your mobile app card, enter the Return address (optional): https://your-domain.com/qovi-retour.
3
Tap Save. An address that fails the checks above is rejected, with the reason in plain words.
  • One address per site. Remove, or emptying the field then Save, deletes it (after confirmation): no more automatic return.
  • The page requires a sign-in less than 5 minutes old; every change is logged and reported by e-mail to the site administrator.
  • The return only applies to requests made with the Alone key (apps without a private key, like DpW). A website does not need it: its return happens in the same browser tab.

Check and troubleshoot

# both files: HTTP 200, content-type application/json, no location: line
curl -sS -D - -o /dev/null https://your-domain.com/.well-known/assetlinks.json
curl -sS -D - -o /dev/null https://your-domain.com/.well-known/apple-app-site-association
# Android: the domain must show as "verified"
adb shell pm get-app-links com.example.app
# otherwise, ask for verification again (the file must be online)
adb shell pm verify-app-links --re-verify com.example.app
# open the return by hand: your app must come to the foreground
adb shell am start -a android.intent.action.VIEW -c android.intent.category.BROWSABLE -d "https://your-domain.com/qovi-retour?x=1"
  • Android verifies the link at installation. Put assetlinks.json online before distributing the app. A phone where verification failed will not see the return until the app is updated (or --re-verify).
  • The app opens twice, or waits forever: check singleTask and taskAffinity="".
  • The app opens on an unexpected screen on return: check flutter_deeplinking_enabled=false.
  • iPhone: Safari opens instead of the app. iOS caches Apple's file: after a change, reinstall the app (or use ?mode=developer during tests).
  • Nothing happens after the vote: the site record has no return address; the address fails the checks (domain, https, port); the outbound link was received more than 3 minutes ago; the outbound link opened in the browser instead of Qovi (Qovi not installed, or the qovi.ch link not yet verified on this phone: qovi.ch's fallback page is shown); or the Qovi version is too old (Qovi from the stores, 1.0.13 or later, recommended). The user can always go back by hand.

Security

  • No private key in the app: only the Alone key and the site's public key.
  • Keychain key in memory only, wiped when locking (60 min of inactivity by default, adjustable) together with the clipboard.
  • Copied password: cleared from the clipboard after 30 s, and on exit.
  • Encrypted and authenticated channels: CH4, CH5 and synchronisation use the G1 envelope = "G1" + base64(nonce 12 + AES-256-GCM + tag 16), with a key derived per use (HMAC-SHA256) and the message direction as associated data. A message that is modified, replayed in the other direction or meant for another transaction is rejected. Everything also goes through TLS.
  • Automatic return: the address comes from the site record, never from the app; only the CH4 GO counts (section 5).
  • Import of an old WL keychain: base64 text of IV + AES-256-CBC(8-byte check + JSON), plain text in Windows-1252 or UTF-8.
